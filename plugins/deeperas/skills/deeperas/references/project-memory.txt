Local storage guarantees neither confidentiality nor backup.

WHAT TO RECORD
While persistence is ON within its authorized scope, record only small, task-relevant facts, confirmed decisions/constraints, unresolved facts and verified results. No secrets, hidden reasoning, raw transcripts, rejected options or unaccepted proposals presented as decisions. Use stable IDs and literal values with their entity, unit, counting basis and time window. Keep unknowns unknown, source conflicts conflicted, and invalidated results stale. A recommendation is not an accepted decision.
Each entry has kind fact/decision/constraint/result; value; state confirmed/unknown/conflicted/stale; provenance [{kind:user/tool/source/calculation, reference, observedAt:UTC timestamp}]; dependsOn:[entry IDs]; and optional validUntil:UTC timestamp for expiring evidence. Provenance references identify the actual user selection/delegation, inspected file and revision, tool observation, primary source and relevant passage, or calculation with recorded inputs. The helper validates structure and dependencies, not the truth of a source: the host must inspect the evidence and confirm its identity, scope and freshness. Saved timestamps alone never prove current truth. Do not store an entry as confirmed until that verification is complete. Confirmed decisions need actual user selection/delegation provenance. Calculations need explicit input dependencies.
For inspected project-local files, attach file:{path:<project-relative file>,sha256:<actual SHA256 of inspected bytes>} to their provenance. Compute the hash with a real tool, never guess it. The helper verifies the exact bytes before confirmation and invalidates that entry and its dependents when the file changes, disappears or becomes unreadable. File provenance cannot escape the actual project. A matching hash proves byte identity, not semantic correctness; user messages and external sources still need host verification.
Use {"action":"put","expectedRevision":<latest returned ledger revision>,"id":<stable ID>,"entry":<entry above>}. Depend on every material fact, accepted constraint and decision used by a result; missing dependency coverage is not proof of independence. Do not attach unrelated entries to make everything reopen. The helper captures input revisions and rejects missing dependencies, cycles, confirmation based on unverified dependencies and stale concurrent writes. On a revision conflict, read/reconcile first; do not blindly replay the old mutation.
